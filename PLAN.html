bosync

A OneDrive/Google Drive-style virtual drive in Windows Explorer, where the "cloud" is a Git repository. Files appear instantly as on-demand placeholders and hydrate from Git blobs only when you open them. Built in (as much as possible) pure Rust.

Cloud Filter API (cldapi) gix · pure-Rust Git windows / cloud-filter crate Platform: Windows 11 Language: Rust

01 The idea in one paragraph

OneDrive, Dropbox and Google Drive's "Drive for Desktop" all sit on the same Windows technology: the Cloud Filter API (a.k.a. Cloud Files / cldapi.dll). It lets a user-space program register a folder as a sync root and fill it with placeholders — files that show up in Explorer with names, sizes and icons but whose contents live elsewhere. When the user opens one, Windows calls back into our program asking for the bytes (hydration). bosync plugs Git into that callback: the placeholder tree is built from a Git commit, and hydration streams the matching Git blob. Editing a file commits it back; pulling from a remote re-projects the tree. The result is a normal-feeling drive whose backing store, history and sync are all Git.

02 How the Cloud Filter API works

Sync root
A directory we register with Windows (CfRegisterSyncRoot / StorageProviderSyncRootManager). Explorer shows it with our branding and a status column.
Placeholder
A file/dir entry with metadata but no data on disk ("dehydrated"). Costs ~0 bytes. Created with CfCreatePlaceholders.
Hydration
On first read, Windows fires FETCH_DATA; we supply bytes via CfExecute(TRANSFER_DATA). The file becomes "available offline" until dehydrated.
On-demand population
Subdirectories can themselves be placeholders; FETCH_PLACEHOLDERS fires when the user browses into one, so we only materialize the tree lazily.
Callbacks
We connect with CfConnectSyncRoot and register a callback table. Windows drives us; we never poll.
Pin / hydration state
Users (or we) can pin files to keep them local, or free up space to re-dehydrate.

05 Mapping OS callbacks → Git operations

Cloud Filter eventWhenbosync does
FETCH_PLACEHOLDERSUser browses into a folderRead the corresponding Git tree, emit one placeholder per entry (file size = blob size, dir = sub-placeholder).
FETCH_DATAUser opens / reads a fileResolve path → tree entry → blob OID, stream blob bytes back via TRANSFER_DATA (chunked).
CANCEL_FETCH_DATAUser aborts a large openStop streaming, free the in-flight read.
NOTIFY_FILE_OPEN/CLOSE_COMPLETIONApp opens then closes a fileTrack dirty state; on close-after-write, mark file for commit.
NOTIFY_DELETE / NOTIFY_RENAMEUser deletes/moves in ExplorerStage equivalent change (git rm / rename) into the working index.
local write (full file)App saves a modified fileConvert placeholder → full file, hash new content, stage blob, commit.

06 Key data flows

Read (hydration)

open file.rs → OS: FETCH_DATA(path,off,len) → resolve path in HEAD tree → gix: read blob @ OID → CfExecute(TRANSFER_DATA) → Explorer shows "available"

Write (commit-back)

save file.rs → OS: NOTIFY_CLOSE (dirty) → read full file from disk → gix: write blob + tree → commit on branch → convert back to placeholder

Remote pull (later)

bosync pull → gix fetch origin → diff old HEAD vs new HEAD → for each change: update / create / delete placeholder → conflicting local edits ⇒ surface as .conflict copies

07 Milestones

  1. Spike & scaffold

    GOAL: a registered sync root that shows up in Explorer.

    Cargo workspace, pick cloud-filter vs raw windows via a throwaway spike, register + connect a sync root over an empty folder, log every callback. Prove the plumbing before any Git.

  2. Read-only Git mount

    GOAL: browse a real repo's HEAD in Explorer; open files; bytes come from Git.

    Project a commit tree into placeholders (lazy via FETCH_PLACEHOLDERS), implement FETCH_DATA from gix blobs with chunked transfer + cancel. This is the headline demo.

  3. Write-back to Git

    GOAL: edit a file in the drive → it becomes a commit.

    Handle dirty-close, deletes, renames; stage and commit through gix; re-dehydrate to placeholder. Single local branch, no remote yet.

  4. Remote sync

    GOAL: pull/push reconcile the drive with origin.

    Fetch, diff HEADs, re-project changed paths, push local commits. Status column reflects synced/modified/conflict.

  5. Conflicts & polish

    GOAL: it doesn't lose data when two sides edit.

    Conflict surfacing (side-by-side .conflict files), branding/icon, basic settings, graceful unmount.

POC stops at M2 (read + write-back works end-to-end). M3–M4 are stretch goals shown for direction.

10 Risks & open questions

Cloud Filter wrapper maturity. The cloud-filter crate may not expose every callback we need. Mitigation: M0 spike validates it early; raw windows bindings are the proven fallback.
Registration friction. Sync-root registration can require running as a packaged app / specific shell registration on Win11. We'll start with the classic CfRegisterSyncRoot path and document any manifest needs.
Identity mismatch. Git tracks content trees; the filesystem tracks paths + mutable bytes. Mapping placeholder file-identity to blob OIDs across edits/renames needs a small local mapping store (path ↔ OID ↔ CF file-id).
Write semantics. Cloud Filter expects us to "upload" on change; we instead commit. Deciding when to commit (every close? debounced?) is a design choice — POC: commit on dirty-close, one commit per save.
Binary/large files. Hydration streams in chunks; very large blobs need bounded memory. POC targets text-ish repos; note the limit rather than solve it.
